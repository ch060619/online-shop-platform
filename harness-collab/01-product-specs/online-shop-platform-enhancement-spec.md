## 功能背景

现有 Online Shop Platform 已实现商品、购物车、订单、登录令牌、统一异常、测试和 Harness 质量门禁，适合作为 Java 后端实习简历主项目继续深挖。当前增强目标不是扩大业务范围，而是围绕高频商品查询、重复下单、订单超时、真实鉴权、压测验证和部署文档，补齐可讲、可测、可回滚的工程化能力。

**当前痛点**：
- 商品列表和详情每次直接访问数据库，缺少缓存命中率与耗时对比数据。
- 下单接口没有幂等保护，重复点击或客户端重试可能生成多笔订单。
- 订单状态只有 `CREATED`、`CANCELLED`，缺少支付、超时和异步超时处理链路。
- 用户密码仍为明文存储，令牌缺少刷新机制，用户端和管理端权限未严格隔离。
- 缺少可复现压测脚本、SQL Explain 记录、Docker Compose 一键启动和完整 OpenAPI 文档。

**预期收益**：
- 将项目从基础 CRUD 电商升级为包含缓存、幂等、消息队列、状态机、安全和压测闭环的后端主项目。
- 所有性能、覆盖率、缓存命中率等数据均来自实际测试或压测结果，避免简历数字失真。
- 每个阶段通过本地 Git commit 保存检查点，便于出错时按阶段回退。

---

## 目标

**主要目标**：
1. 为商品列表和详情增加 Redis Cache-Aside 缓存，支持空值缓存、TTL 随机化、热点商品预热和缓存命中率统计。
2. 为下单接口增加 `Idempotency-Key` 幂等语义，使用 Redis+Lua 原子处理重复点击、重试和并发提交。
3. 扩展订单状态机为 `CREATED / PAID / CANCELLED / TIMEOUT`，使用 RabbitMQ TTL/DLX 延迟队列处理超时未支付订单并回补库存。
4. 将明文密码升级为 BCrypt，登录响应 access token 与 refresh token，并区分 USER 与 ADMIN 权限。
5. 提供压测脚本、SQL Explain 记录、Docker Compose 一键启动、OpenAPI/Swagger 和核心流程图。

**成功指标**：
- 订单幂等并发测试中，同一用户同一 `Idempotency-Key` 的 10-50 次并发请求最多生成 1 笔订单。
- RabbitMQ 超时消息重复投递时，已支付、已取消、已超时订单不会重复回补库存。
- 所有新增业务代码均同步测试，后端 `mvn clean verify -Pharness-new` 与显式 JaCoCo 校验通过。
- 压测报告记录机器配置、数据量、并发数、QPS、P95、P99、错误率、缓存命中率，数字只来自实际执行结果。

## 用户故事

### 故事 1：商品缓存加速

**As a** 访客或普通用户  
**I want** 高频商品列表和商品详情可以快速返回  
**So that** 浏览商品时系统响应更稳定，数据库压力更低

#### 验收标准

- **Given** 商品列表查询条件相同且缓存未过期  
  **When** 用户重复访问商品列表接口  
  **Then** 系统优先从 Redis 返回缓存结果，并记录缓存命中指标

- **Given** 用户查询不存在的商品 ID  
  **When** 短时间内重复查询该商品详情  
  **Then** 系统使用空值缓存避免缓存穿透，过期后允许重新访问数据库

- **Given** 管理员新增、更新或删除商品  
  **When** 商品写操作成功提交  
  **Then** 系统删除相关详情缓存和商品列表缓存，后续查询返回最新数据

#### 异常场景

- **Given** Redis 短暂不可用  
  **When** 用户访问商品列表或详情  
  **Then** 系统降级访问数据库，不因缓存异常导致商品查询失败

---

### 故事 2：订单幂等防重复提交

**As a** 普通用户  
**I want** 重复点击提交订单或网络重试不会创建多笔订单  
**So that** 我不会因为客户端重复请求产生重复购买

#### 验收标准

- **Given** 用户购物车有效且携带新的 `Idempotency-Key`  
  **When** 用户提交订单  
  **Then** 系统创建一笔订单并将幂等结果记录到 Redis

- **Given** 同一用户使用同一 `Idempotency-Key` 和相同请求体重试  
  **When** 首次请求已经成功  
  **Then** 系统返回同一笔订单结果，不再扣减库存、不再创建订单

- **Given** 同一用户使用同一 `Idempotency-Key` 但请求体不同  
  **When** 用户再次提交订单  
  **Then** 系统拒绝请求并返回幂等冲突错误

#### 异常场景

- **Given** 首次请求仍在处理中  
  **When** 同一 `Idempotency-Key` 的并发请求到达  
  **Then** 系统返回处理中或冲突提示，不创建重复订单

---

### 故事 3：订单状态机与超时处理

**As a** 普通用户  
**I want** 订单可以支付、取消或在超时后自动关闭  
**So that** 库存能随订单状态正确流转

#### 验收标准

- **Given** 订单状态为 `CREATED`  
  **When** 用户模拟支付成功  
  **Then** 订单状态变为 `PAID`，记录支付时间，超时消息到达后不会回补库存

- **Given** 订单状态为 `CREATED`  
  **When** 用户取消订单  
  **Then** 订单状态变为 `CANCELLED`，库存只回补一次

- **Given** 订单超过支付截止时间且仍为 `CREATED`
  **When** RabbitMQ 超时消息投递到消费者
  **Then** 订单状态变为 `TIMEOUT`，库存只回补一次

#### 异常场景

- **Given** 订单已支付、已取消或已超时
  **When** 用户再次支付、取消或 RabbitMQ 重复投递超时消息
  **Then** 系统拒绝非法状态流转，不重复回补库存

---

### 故事 4：真实鉴权安全

**As a** 用户或管理员  
**I want** 系统用安全密码存储、令牌刷新和角色权限保护接口  
**So that** 用户端和管理端职责清晰，敏感操作不会被普通用户执行

#### 验收标准

- **Given** 用户密码已使用 BCrypt 存储  
  **When** 用户使用正确密码登录  
  **Then** 系统签发 access token 与 refresh token

- **Given** access token 过期但 refresh token 有效  
  **When** 用户调用刷新令牌接口  
  **Then** 系统返回新的 access token 和 refresh token

- **Given** 普通 USER 用户  
  **When** 访问商品新增、更新或删除接口  
  **Then** 系统拒绝访问

## 非功能性需求

### 性能要求

- 商品缓存阶段必须记录缓存前后商品列表与详情接口耗时对比。
- 压测阶段必须记录机器配置、数据量、并发数、QPS、P95、P99、错误率和缓存命中率。
- 不允许在未执行实际压测、测试或代码实现前，将性能数字写入简历或交付摘要。

### 安全要求

- 密码不得明文存储，种子用户也必须使用 BCrypt hash。
- refresh token 需要可过期、可撤销，不能明文泄露到日志。
- 管理类接口必须进行角色校验，Controller 不直接访问 Repository。

### 兼容性要求

- 保持现有 `/api` 路径和统一响应结构兼容。
- 登录响应保留旧 `token` 字段作为 access token 兼容现有前端。
- SQLite 继续用于本地开发测试，Docker 环境以 MySQL、Redis、RabbitMQ 为主。

### 可用性要求

- Redis 缓存异常不得导致商品查询失败。
- RabbitMQ 超时消息必须幂等消费；定时任务兜底执行时也必须保持重复扫描幂等。
- 每个阶段通过两轮质量检查并本地 commit 后再进入下一阶段。

## 排除范围

本次迭代不包含以下内容：

- 真实第三方支付、退款、物流和优惠券。
- 多商户、评价、收藏、推荐系统。
- 生产级可观测平台接入，如 Prometheus、Grafana、ELK。
- RabbitMQ 集群、高可用 Redis 集群和灰度发布。

**后续迭代计划**：
- 将压测报告中的真实数据整理成简历项目亮点。
- 对 RabbitMQ TTL/DLX 与插件型 `x-delayed-message` 两种延迟消息模式做后续对比。
